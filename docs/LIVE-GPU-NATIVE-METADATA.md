# Typed textures with Windows-generated sharing metadata

Three fresh owned QEMU/WHPX runs on 2026-10-10 each rendered two NVIDIA shader
frames and consumed them on the Windows GPU with matching pixels. The new
opt-in supplies a public texture description and generates the host resource's
runtime sharing metadata through the native Windows runtime. Linux runtime
metadata and driver allocation data are still returned unchanged to the guest.

This is an experimental interoperability path, not a stable driver ABI or an
accelerated Omarchy desktop. Both attempted presentation runs in this checkpoint
failed DXGI frame statistics. Their imports, first GPU copy and first backbuffer
pixels succeeded, but no completed presentation is claimed for those runs.
The earlier [presentation checkpoint](LIVE-GPU-PRESENTATION.md) remains historical
evidence; the newer failures mean presentation stability is unproven.

[Hardware evidence](evidence/QEMU-LIVE-GPU-NATIVE-METADATA-2026-10-10.json)
preserves all eight new runs and the preceding seven-run matched experiment,
including failures, exact executable/source hashes, selected receipts, complete
cleanup and hashes of the original private reports/logs. No opaque metadata
bytes, proprietary binaries or private guest images are published.

## Why introduce a public texture description?

The original `OpenSharedHandle` path intermittently returned `E_NOINTERFACE`.
Independent native KMT opens confirmed that Windows retained the guest's
264-byte metadata without transport corruption. A native Windows resource with
the same public texture properties generated 280 bytes. These sizes are measured
on this driver/runtime combination, not portable metadata layouts.

A matched warm-up experiment generated a native template in both variants.
The original guest metadata passed two of three runs; one failed both import
stages. Substituting Windows-generated metadata passed four of four runs.
This motivated the new operation. The sample does not prove the root cause or
establish a stable fix. No private field is inferred from offsets, padding or
the size difference.

## Explicit operation and ownership

`--driver-native-metadata` requires `--driver-shared-resources` and its existing
allocation, context, query and owned-QEMU gates. Capability bit 30 enables
`CreateNativeSharedVendorResourceAllocation` (`0x205b`). Its 48-byte descriptor
contains the existing bounded allocation/runtime lengths plus width, height,
format and resource flags. The initial accepted profile is:

| Property | Diagnostic value |
| --- | --- |
| Texture | 2D, 130×73, one array slice and mip |
| Format | RGBA8 UNORM (`28`) |
| Resource flags | ALLOW_RENDER_TARGET (`1`) |
| Sample count / quality | 1 / 0 |
| Heap | DEFAULT, SHARED, node masks 1 |
| Layout / clear value | UNKNOWN / absent |
| Native template initial state | COMMON |
| Native allocation size / alignment | 65,536 / 65,536 bytes |

The diagnostic `native` workload calls `wddm_bridge_prepare_native_texture`
immediately before creating the shared render target. The declaration binds to
the sole owned device and calling thread. Duplicate, unsupported, cross-thread
and unowned declarations fail. A failed shared allocation attempt consumes the
declaration; device destruction clears it. This hook is diagnostic-only and
does not replace general DRM resource creation.

Windows creates a same-adapter D3D12 template and shared handle, opens it through
an independently owned KMT adapter/device, queries bounded metadata sizes and
obtains the actual bytes with `D3DKMTOpenResourceFromNtHandle`. It destroys that
KMT resource/device/adapter, closes the handle and releases the prototype. A
scoped lease also cleans these objects on exceptions; uncertain cleanup stops
the worker. The generated bytes stay local and are applied only to the typed
allocation's native `pPrivateRuntimeData`. Existing typed allocation/resource
ownership, packet limits, budgets, retirement and rollback still apply.

The NVIDIA allocation driver-private data remains vendor-specific and comes
from the guest runtime. The Linux metadata bytes are preserved in the wire
reply and verified by the guest shim. The original shared-resource operation
continues to use its original metadata, even when the new capability is enabled.
Generation happens at resource creation, not at each frame handoff.

Microsoft documents the [KMT resource-open operation](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmthk/nf-d3dkmthk-d3dkmtopenresourcefromnthandle).
Its [D3D12 OpenSharedHandle contract](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12device-opensharedhandle)
describes handles created by `CreateSharedHandle`. These APIs do not document
reusing opaque runtime metadata for a separately created vendor allocation.
Successful tests here do not establish that such reuse is supported across
drivers, runtime versions or other texture profiles.

## Physical results and controls

| New case | Result |
| --- | --- |
| Consumption 3, 4 and 5 | Each passes both imports, two actual frame comparisons, 14 retired commands and four retired guest signals |
| Presentation 1 and 2 | Both imports and first GPU/backbuffer frame pass; `Present` and its queue fence succeed, but statistics remain count 0 / QPC 0; overall rejection preserved |
| Wrong workload | Underlying typed operation and two GPU frames pass; requesting the older `consume` workload keeps all public success fields false |
| Missing native opt-in | Guest declaration fails before a typed allocation; no metadata generation or import receipt; overall rejection preserved |
| Older consume image, capability enabled | Passes two frames through the original operation; no metadata generation; native metadata success remains false |

Every run ends with host exit 0, owned QEMU exit 0, no forced stop, no fence
control failure, no pending submissions/signals, no live tracked native objects
and no cleanup failures. Native templates also report successful separate
resource/device/adapter/handle cleanup. Failed presentation runs are not retried
in place or rewritten as successes.

Each successful final frame has dense RGBA SHA-256
`fd894f123883a31e65cea02dc84eb9a52f0356511b4a85eb41977d8c46814353`,
matching the [published shader image](images/nvidia-guest-shader-triangle-2026-10-10.png).
The two failed presentation runs also export a correct first-frame backbuffer;
pixel correctness is separate from completed display evidence.

MSVC `/W4 /WX`, four native ownership/protocol contracts, 78 CLI rejection cases,
44 milestone guard groups and 191 Linux bridge fault cases pass. New fault cases
cover declaration ownership, malformed profiles, duplicate declarations,
cross-thread use, failed-attempt cleanup and capability rejection.

## Remaining work

Investigate the zero DXGI statistics without weakening display acceptance.
Broaden import reliability testing across fresh boots and driver/runtime versions,
and replace the diagnostic profile/hook with a supported general resource
creation path. Integrate the guest kernel/DRM transport, retained shared GPU
fences, the actual Omarchy/Hyprland window, resizing and recovery. CUDA, OpenGL,
Vulkan, video acceleration and at least 93% of native performance still require
implementation and independent [product acceptance](PRODUCT-ACCEPTANCE.md).
CPU-synchronized handoffs, full-frame readbacks and the visible diagnostic pause
remain unsuitable for the production frame path. The launcher does not select
this backend.
